Building a Game with an AI Partner

A field guide from five weeks and 700+ small steps · November 2026
The short version: the AI proposes, you decide, and every step is small enough to check, even from a phone. That one rule took my game, Gloamdeep, from an empty folder to version 0.3.454 in about five weeks: roughly 730 pull requests and 1,000 written decisions, every one of them mine. An AI coding assistant is a fast, tireless builder with no memory between conversations. Everything below does two things: it keeps the AI from guessing, and it gives the AI a memory made of small files. It works with any engine and any AI coding tool.

Ten habits that made the biggest difference

1
Propose before building. The AI says what it found, gives 2–3 options with one recommended, and waits for your pick. Nothing gets built on a guess.
2
Multiple choice, always. You get options to tap, plus "your own answer." It's fast to answer, you keep the last word, and the recommended pick is usually right.
3
It never invents. It never makes up mechanics, names, story or numbers. Anything undecided goes in an open-questions file, and the AI asks you. The game stays yours.
4
One small visible change per step. "The hero can move one tile." Small decisions can be grouped, but never a new mechanic plus a new system at once.
5
Write every decision down with an ID, a date and the reason (D-001…). Never edit an old one; a new one replaces it. "Why is it like this?" always has an answer.
6
A project memory in small files. A rules file the AI reads first, a progress file with "Next up," a decisions log and a glossary. Each file stays under 8 KB, and a test checks that.
7
Fresh conversation for each step. Long chats get slow and muddled. A fresh start reads the progress file and only the docs the next step needs.
8
See it before you accept it. For each visible change, a build you can play right away. Sounds get a board of buttons. Art gets 3 mock-ups side by side.
9
Measure, don't guess. Check the real screen size, time the slow part, and replay the bug before offering a fix. Several "obvious" fixes turned out wrong once measured.
10
Turn repeated chores into tools. When hand-done bookkeeping slipped, it became a small script plus a test that fails when the step is skipped.
Two more worth stealing: an audit every 40 versions that trims the docs and archives old material, deleting nothing; and a lessons file where each step adds one line about working together.
Set the pace on day one. Agree on the pace in your first conversation and write it down as a decision. Mine started as "slow and tiny." That was too slow on day one, so I changed it the next day.

Tips by setup

Pick the cards that match how you work; most people fit two or three.

If you're new to code

Safety nets come first
  • Use version control (git) from day one. Every step can then be undone. A free GitHub account is enough.
  • Never let the AI change your main copy directly. It works on a branch, and you merge once you've tried it.
  • Ask it to explain terms the first time they come up. Put that rule in your rules file.

If your AI runs on its own for long stretches

Background agents, overnight runs, several agents at once
  • One "Next up" line it must follow. When a choice is yours, it asks and stops instead of choosing for you.
  • Fresh sessions per step, not one endless chat. The memory files carry the context.
  • Plan the method before big runs. Settle how you'll review the results, and ask for them in a strict one-line format a script can check.

If you work from a phone

Cloud AI sessions, a PC that stays off
  • Put the project online (GitHub, for example) so a cloud AI can work on it while your PC stays off.
  • Make answers tappable: every reply ends with 2–4 numbered options. You can answer with just "2".
  • Keep replies short: "handoff in 5 lines or fewer."
  • Have a playable build on your phone before you accept a change. Many engines can export to a web page.

If your engine saves binary files

For example, Unreal assets, or Unity without text mode
  • The AI can't read binary files, so keep what matters in text: rules and tuning in code, config or data tables exported to CSV/JSON, and design notes in Markdown.
  • Turn on text formats where the engine has them. Unity can save assets as text. Godot scenes and RPG Maker MZ data are already text.
  • Close the editor before pulling the AI's changes, or the editor may save over them.
  • Let it prove things: run the engine's tests from the command line, with a test added for each fix.

Copy this to start

Save it at the root of your project under the name your tool reads, such as CLAUDE.md for Claude Code or AGENTS.md for Codex. Make the files it names, then fill in the bracketed part.

# [Game name]: notes for the AI

## I lead. Work in tiny steps.
- Propose before building: what you found,
  2-3 options, recommendation first.
  Wait for my pick.
- Ask as multiple choice (2-4 options,
  recommended first). I can always give
  my own answer.
- One small visible change per step.
- Never invent mechanics, story, names or
  numbers not in docs/DECISIONS.md. Add
  gaps to docs/OPEN-QUESTIONS.md and ask.
- Plain words. Explain technical terms
  the first time.

## Start of every conversation
1. Pull the latest main.
2. Read docs/PROGRESS.md (Next up, waiting
   on me, last 3 logs).
3. Read only the docs Next up names.

## Records
- Every decision: ID, date, why. Never
  edit one; supersede it.
- Keep every doc under 8 KB. Archive old
  material, never delete.
- One word, one meaning: docs/GLOSSARY.md

## Handoff
- Never push to main. One pull request
  per step; I merge.
- Give me a way to try it before
  I accept it.
- Handoff in 5 lines or fewer.

## Hard rules
- [engine, folders, what must stay text,
  how to run tests]

Lessons from bugs and growth

These are lessons from building the game itself rather than from working with the AI. Most of them apply to any engine.

What bugs taught me

Each one cost time once
  • Old saves must always load. A save from an older version gets upgraded, never thrown away. Every change to the world or the save asks: "what does an older save see?"
  • Each random roll gets its own seed. Two things rolled from the same number quietly depend on each other. In my game, one roll ended up hinting at another.
  • Other players find what you don't. A friend's playtest found a freeze. The fix came with a safety net: an error in one frame is logged once, and the game keeps going.
  • Docs drift from the code. One audit found five docs that no longer matched the code, and a later one found nine more. Audits now check the docs against the code.
  • Keep the tests fast. Slow tests get run less. Mine went from 59 to 35 seconds by building test data once and splitting the slowest test.
  • Hunt bugs on a schedule. At each audit, a helper reads the new code and checks each finding with a small script. I pick which to fix, and each fix is its own small step with a test.

How the game grew

Stages, groundwork and seeing the whole
  • In stages. The first stage was planning only: decisions and art studies, no game. Then came the foundation, one small visible step at a time. Each later stage began with a plan I picked.
  • A playtest of the whole sets the next plan. After the foundation, I played it through. The caves felt boxy and samey, so the next stage began with natural caves.
  • Groundwork first. Before a big feature, a few steps that change nothing on screen, such as upgrading old saves. Then the feature comes quickly and safely.
  • Only what works shows. A button appears once its feature exists. Nothing is greyed out as a promise.
  • Dev tools in every build. Spawn anything, jump to any level, god mode, and saved test spots that reload a moment of play. A playtest goes straight to the thing being tried.
  • Plan the whole before the parts. The full scope was drawn up as multiple-choice questions, and each big feature is planned as numbered steps first.

Design habits

A
Mock-ups before art. New looks are shown as pictures first, then built, then checked against the mock-up. Mock-ups reuse the game's own sprites.
B
One frozen look. The art study you love is never edited. Style rules are drawn from it.
C
The story in one place before quests. A single lore file came first, so every character's lines and every quest build on it.
D
Outside reviews are ideas, not decisions. Suggestions go into a research file, and none of them counts as decided until you pick it.
E
Plan for the end early. Start the store checklist long before release, and build each piece when it's due, so nothing blocks launch.
F
Research beside building. Helper agents research while the main conversation builds, but only one conversation builds at a time.
